# API reference

The web UI is a client of this JSON API. Reading and day-to-day work can be scripted with an API token; some
routes are for a signed-in person only (below).

## What an integration can and cannot do

* **Tokens are viewer or editor, never administrators.** A token can read everything a viewer reads on the sites
  its creator may read (devices, alerts, incidents, findings, coverage, topology, reports list, exports, `/metrics`)
  and, as an editor, do day-to-day work: acknowledge and resolve alerts and incidents, edit and import devices, run a
  scan, make a report, manage work items, ask the AI features. Every route whose lowest role is administrator
  answers a token `403 {"code": "forbidden"}`: users, tokens, the audit log, settings, rules, zones and policies,
  switches, connectors, backups, updates.
* **Actions on devices need a signed-in person with the password.** Planning, applying, extending and releasing a
  block, quarantine or port action, and changing who may do them, are refused to a token (and under
  `--insecure-no-auth`) even if the role were enough: the handler checks that a person signed in, is an
  administrator with access to every site and holds the permission of the action. Applying asks for the password
  again.
* **Automation and Autopilot need a person with a typed phrase.** Switching on automatic enforcement
  (`AUTOMATIC ENFORCEMENT`), letting Autopilot block (`LET AUTOPILOT BLOCK`) and making a rule act by itself
  (`go-live`, `AUTOMATIC ENFORCEMENT`) need a signed-in administrator who may act, the password and the phrase.
  Switching them off never needs a password.
* **New in 4.2.1**: an [OpenAPI description](#openapi) of this API. **Planned**: narrower tokens (limited to chosen
  route groups). This page stays the prose reference; the [Access matrix](#access-matrix) says who may call what.

## Stability

This is the same API the console's own UI uses — there is no separate, narrower surface reserved
for third-party integrations. In practice that means:

* Endpoint paths and their meaning (`GET /api/assets` lists devices, `POST /api/alerts/{id}/ack`
  acknowledges an alert, and so on) are stable — the UI depends on them too, so a breaking rename
  would break DENIS's own console, not just an integration. A route that had to go for safety is retired with
  `410 {"code": "retired"}` rather than removed, and a refused field answers `400`; both are listed in
  [Changes since 4.0](#changes-since-40).
* Response bodies are today's internal data shapes serialized directly (an asset's JSON is close to
  its stored form). Fields are additive over time — a new field can appear, an existing one keeps
  its name and meaning — but treat an unfamiliar field as ignorable rather than assuming the shape
  is closed. `Event.raw_details` in particular is intentionally free-form and varies by alert kind;
  do not depend on its exact keys beyond what the alert you're handling documents.
* There is currently one version of this API — no `/api/v1/` prefix, no version header. If a
  genuinely breaking change is ever needed, it will get one then, rather than speculatively now.

## Authentication

* **Sign in**: `POST /api/auth/login` with `{"username": "...", "password": "..."}`. The response sets a
  `denis_session` cookie (HttpOnly, SameSite=Strict, `Secure` behind TLS). Send the cookie on later requests.
* **CSRF protection**: every request that is not `GET` must carry the header `X-Denis: 1` (a request with an
  `Authorization: Bearer dnt_…` header is exempt). Without it the answer is a plain-text `403 missing X-Denis header`.
* A user whose password was set by an administrator must change it first (`POST /api/auth/password`); until
  then every other endpoint answers `403 {"code": "must_change"}`. When the sign-in policy requires a second step or a
  passkey that the person has not set up, every route outside `/api/auth/` answers `403` with `code: mfa_required` or
  `passkey_required`.
* Errors are JSON: `{"error": "…", "code": "…"}`. The codes the authentication layer uses: `unauthenticated` (`401`,
  not signed in), `forbidden` (`403`, role too low, or a route a token may not use), `must_change`, `mfa_required`,
  `passkey_required`, `rate_limited` (`429`, see `Retry-After`). Handlers add their own codes, named in the rows below.

```bash
curl --cacert tls/ca.pem -c jar -H 'X-Denis: 1' -H 'Content-Type: application/json' \
     -d '{"username":"admin","password":"…"}' https://localhost:8080/api/auth/login
curl --cacert tls/ca.pem -b jar https://localhost:8080/api/assets
```

### API tokens (for scripts and integrations)

An administrator creates a token on the **Users** tab (or `POST /api/api-tokens` `{"label": "Grafana", "role":
"viewer"}`); the value (`dnt_…`) is shown once. Send it as a bearer token:

```bash
curl -H 'Authorization: Bearer dnt_…' https://denis.example.com/api/assets
```

* Role is **viewer** (read) or **editor** (also change assets, acknowledge alerts, start scans); a token can
  **never** be an administrator, so a leaked token cannot manage users, tokens or read the audit log.
* No `X-Denis` header and no cookie are needed; when an `Authorization` header is present *only* the token is
  considered. Tokens cannot use `/api/auth/*` (they have no password or session; `403 forbidden`), except
  `GET /api/auth/me`.
* A token acts as the account that created it, with the token's own role: it shares that account's site access
  and its own-view state (for example the read marks and muted categories of the notification centre).
* Only a hash is stored. Revoke with `DELETE /api/api-tokens/{id}`: it stops working immediately. The audit
  log records changes made by a token as `token:<label>`.
* A token lives with the administrator who created it: it stops working while that account is disabled or
  once it is deleted, and it never acts above that account's current role (a token made by an admin who is
  later made a viewer is a viewer). A token also takes the **per-site access settings of the account that
  created it** (`PUT /api/users/{id}/site-access`; no setting means every site). Administrators themselves are never
  restricted by those settings, but the viewer or editor tokens they create are, and changing the creator's settings
  changes the token's reach at once. A token whose creator cannot be identified (one created
  before creators were recorded, listed as "creator unknown" in `GET /api/api-tokens` as `creator_state`) works for
  nobody. On a multi-tenant install a token only works on the console of the tenant it was issued in.
* Prefer a token per integration so one can be revoked without breaking the others.
* **Rate limits**: a valid token is capped at 300 requests/minute (a sliding window; comfortably above any
  reasonable polling interval, meant to catch a runaway loop or a compromised token, not to slow down normal
  use) — `429 {"code": "rate_limited"}` past that. Repeated *wrong* tokens from one address are throttled
  after 10 failures in 60 seconds, independent of any one token's own limit, so a guessed/brute-forced token
  cannot be tried indefinitely.

## OpenAPI

`GET /api/openapi.json` returns an OpenAPI 3.1 description of every route of the console. It needs a signed-in
user (a session or a viewer API token), like `/docs`; it is not public. The same file is attached to every release
as `openapi.json`, with `info.version` set to the release version. It is not listed in `SHA256SUMS` (that list
holds the programs and the installer); the release also carries `openapi.json.sha256`.

The description is generated from the tables that enforce access, and tests hold it to them. Each operation
carries these extensions:

* `x-denis-role`: the lowest role (`viewer`, `editor` or `admin`; `any` for the account pages under `/api/auth/`,
  which every signed-in user has; `operator` for the `/api/operator/` routes, which need an MSP operator's own
  sign-in, the `denis_operator` cookie of the `operator` security scheme; `public` for routes that need no sign-in).
* `x-denis-token`: `true` when an API token may call the operation (of the account pages only `GET /api/auth/me`).
* `x-denis-msp-class`: the class when an MSP calls it over the management channel (Read, Configure, Admin, Enforce
  or Never). `x-denis-msp-class-max`: the class the request body can raise it to (a policy update that switches on
  automatic enforcement is Enforce; a device-link edit or an unbinding is Admin). Creating an administrator is
  checked separately.
* `x-denis-install-wide`: the operation is refused on a customer console of a multi-customer install.
* `x-denis-person`: a person must call it, never an API token: a signed-in administrator, or an MSP operator over the
  management channel with the Full level, the ticked box and a fresh second factor.

Request and response bodies are generic objects in this version; the tables below stay the reference for fields.

To pin the description for code generation, download it from the release (or from your console) and keep it with
your integration; compare it after an update to see which operations were added or changed. When building DENIS
from source, `DENIS_WRITE_OPENAPI=1 cargo test --lib openapi` rewrites `docs/openapi.json`, and a test fails when
the file no longer matches the code.

### Rule actions

New in 4.2 (see [Rule actions](enforcement.md#rule-actions)); the automatic choice is **Experimental**. All of it is
additive: `offer_block` of 4.1 keeps working. `offer_block: true` from an old client means "prepare" for a policy
without a setting of its own; unticking it means "only notify". The 4.1 way of marking a policy through
`PUT /api/policies/{id}` with `auto_enforce` is refused since 4.2 (it made a rule act at once, without the trial):
choose the automatic response under the rule instead. A mark acts only together with a live automatic setting that
names the same action, connector and method.

For a connection block of an IT rule, `prepared.target` carries `direction_unknown: true` and a `provenance` with the direction and port `inferred` (flow records keep no direction); `POST /api/nac/actions/plan` takes `direction_unknown: true` on a flow target and then warns `direction_unknown` |
| `POST /api/nac/prompts/{id}/dismiss` | administrator who may act, no password | `{disposition: not_now\|expected_behavior\|false_positive, snooze_hours?: 1 to 168 (the console offers 4, 24, 72), note?}`. "Not now" hides it until the rule matches again after that time (and a rule set to respond automatically does not act on it meanwhile, nor does its trial count it); the other two close it and stop new responses for this device and rule until the rule changes. `404` when it is not waiting any more. Audited as `nac.prompt.dismissed` |
| `POST /api/nac/prompts/{id}/review` | administrator who may act and holds the permission of the prepared action | the prefill of the plan dialog, computed fresh: `{target, action, instance_id, method, duration_minutes, origin: {kind: prompt, id}, prepared}`. It never creates a plan or acts; the plan, the reason, the ticks and the password stay with `POST /api/nac/actions/plan` and `apply`. Audited as `nac.prompt.reviewed` |
| `GET /api/nac/rule-trials?policy_id=` · `POST /api/nac/rule-trials/{id}/judge` | administrator who may act | what a rule set to respond automatically would have done, the last 90 days, newest first: `{policy_id, rule, kind, trial: {started_at, live_at, records, judged, agree, wrong_device, ready, day}, records: [{id, at, asset_id, device, verdict: would_act\|would_skip, plan, judged, judged_by, judged_at}]}` · `{verdict: agree\|disagree\|wrong_device}` (audited as `nac.rule_trial.judged`; never over the MSP channel: a remote console could otherwise judge its own rule's trial and then go live) |

A notice about a prepared response (category `enforcement`, one per rule per hour, the repeats folded into it) links to
`#/enforcement/proposal/<id>`; `#/enforcement/proposals?rule=<policy id>` opens one rule's. The link only opens the
console; nothing is approved from a link, a notification or the bell.

### Connector configuration

`POST`/`PUT /api/nac/connectors` take a kind's settings in `config` and its secrets in `secrets`, keyed by the secret's
name. A secret is never returned (`secrets_present` says which are set); a blank one on a `PUT` keeps the stored one,
and changing where the connector connects while keeping it needs `password` (`403 reauth_required`). The complete list of every kind's fields, with labels and help, is `kinds[].fields`
of `GET /api/nac/connectors`; the two kinds that changed most in 4.2:

| Kind | `config` | `secrets` |
|---|---|---|
| `unifi` (UniFi Network controller, one site) | `address`, `site` (the site's short name), `auth`: `password` \| `api_key` \| `both` (4.2: an API key reads clients and adds or removes DENIS's own firewall policies; disconnecting a wireless client and changing switch ports still need the local account), `username`, `unifi_os` (a UniFi OS console), `quarantine_port_profile` (name or id; empty switches the port quarantine off), `protected_macs[]`, `manage_rules` (4.2, default off: DENIS may create its own block-only firewall policies, named `denis-…`, when it signs in with an API key), `fw_block_gateway` (4.2, default off: those policies also block the device's access to the gateway), `fw_max_policies` (4.2, 1 to 500, default 50), `verify_tls`, `protected_cidrs[]` | `nac.unifi.password`, `nac.unifi.api_key` (4.2) |

## Agent ingest API (port 8081)

Used by `denis agent`; documented for completeness. `Authorization: Bearer <agent token>`.

* `GET /api/v1/ping` → `200` if the token is valid.
* Agent updates (4.1, additive both ways). `POST /api/v1/report` may carry `update`: `{target, manual_needed, installing,
  last: {at, version, ok, message}}` (the agent's platform, why it cannot replace its own program, the version it is
  installing, the last attempt); absent from reports by agents before 4.1, ignored by a master before 4.1. The answer
  may carry `command`: `{action: "update", version, source: "release"|"master", mirror: true|false}`, absent when there
  is nothing to do and from masters before 4.1, ignored by agents before 4.1. The command is read only from this answer
  and acted on only if the version is strictly newer than the agent's own, its signature verifies against the release key
  built into the agent, and it is built for the agent's platform. `GET /api/v1/agent-build/{version}/{file}`
  (`SHA256SUMS`, `SHA256SUMS.sig`, `denis-<platform>`) hands an agent the build it was asked to install when the source is
  `master`: `404` for anything else (another version or platform, an agent nobody asked, another tenant's agent), `429`
  with `Retry-After` when builds are being handed out to others or the agent has had its few builds for the hour.
* `POST /api/v1/report` → `{agent, run_id, seq, sent_at, assets[], flows[], signals[], conversations[]}`, plus
  `flows_v6[]`, `signals_v6[]`, `conversations_v6[]` and `east_west_v6[]` from an agent running with `--ipv6` (absent
  from older agents' reports; the IPv6 industrial and east-west records are kept out of `conversations[]` and
  `east_west[]` so a master of an older version still reads the rest of the report).
  Batches are idempotent per `(run_id, seq)`; the token is bound to `agent.id`. A batch is recorded as applied right after its
  devices are saved and before its flow, conversation, DNS and alert counts, so a retry after a failure in between is
  acknowledged as a duplicate and is never counted twice (the price: a batch cut off half-way has the rest of its counts missing).
* `POST /api/v1/msp-sync` is the separate path a customer's own master uses with `denis run --report-to`
  (devices and already-scored alerts, see [Deployment](deployment.md#msp-live-devices-and-alerts-from-a-customers-own-master));
  the same token kind, a different payload. Backups pushed with `--backup-upstream` use their own upload endpoint
  on this port too (`POST /api/v1/backup`, a SQLite file up to 500 MiB, streamed to disk).
* `GET /api/v1/msp-channel/hello`, `POST /api/v1/msp-channel/poll`, `POST /api/v1/msp-channel/reply` (Experimental,
  4.1): the MSP management channel ([MSP management](msp-management.md)). A customer's own master, paired with an MSP,
  long-polls the MSP's ingest port for signed requests and posts the answers; authenticated with the token of kind
  `msp_relay` the MSP issued for that customer. A token reaches only its own customer's queue. Not for integrations.
* Answers an agent should retry later, not drop (the agent keeps its spool): `429` with `Retry-After` (this tenant's
  limit of reports being applied at once, its requests per minute for one token, or backups being received),
  `503` (the tenant is suspended). `507` on a backup upload means the tenant's quota for agents' backups is used up
  (`413` is the 500 MiB cap). The limits are set per tenant by the MSP (see [Multi-tenancy](multi-tenancy.md)).
